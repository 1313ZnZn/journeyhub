Scope of this delivery: English UI, interactive design prototype and implementation plan. The prototype uses example itineraries and simulated tasks. The AI provider will be selected later. No AI service, ticket provider, payment service or email provider has been activated.
01 / Product direction

A travel companion that follows through

Help a traveler discover relevant experiences, turn them into a realistic itinerary, and complete approved tasks with visible receipts. Start with Bangkok, Shanghai and Singapore. The first production release covers local experiences; flights and hotels need separate supplier integrations.

1

Discover

Ask about dates, companions, budget, interests, pace and accessibility needs.

2

Shape the day

Offer a sourced itinerary. Explain fit, cost, travel time and unresolved details.

3

Review actions

Confirm specific items, travelers, prices, cancellation terms and reminders.

4

Follow through

Execute approved tasks, reconcile receipts and notify the traveler of changes.

04 / Real AI integration

The model proposes. The application verifies.

English UI

Supabase sign-in, trip brief, streamed conversation and itinerary cards.

Server orchestrator

Authenticated Edge Function. Load allowed context, call the chosen model, validate outputs and enforce limits.

Approved tools

Read the catalog, obtain quotes, validate schedules, propose tasks and inspect task status.

Task worker

Process approved jobs, call provider APIs, record receipts and reconcile callbacks.

  1. Provider-neutral gateway: accept a normalized request and return structured suggestions, itinerary items, citations and proposed actions. Choose the model after testing tool use, planning accuracy, latency and cost on the three cities.
  2. Grounding: retrieve current Supabase catalog entries and supplier results first. A recommendation must reference a real catalog or provider ID; new sightseeing suggestions remain labeled as unverified and cannot be booked.
  3. Structured response: include summary, itinerary_items, evidence, unresolved_questions, proposed_actions. Each item carries destination, timezone, duration, cost, currency and an availability timestamp. Schema validity is followed by business validation.
  4. Schedule validation: check local dates, daylight-saving rules where relevant, transit buffers, opening hours, capacity, party size and the traveler’s budget. Keep estimated costs distinct from provider quotes.
  5. Tool boundary: tools have narrow schemas and explicit permissions. The model does not receive SQL execution, raw credentials or unrestricted payment access. External pages and provider descriptions are treated as data.
  6. Operational limits: enforce per-user quotas, maximum tool calls, timeouts, context limits and spend alerts. Save resumable state. An unavailable AI must return a visible error rather than a fabricated successful response.

If OpenAI is selected, Responses API function calling can connect the model to application tools, and Structured Outputs can define the UI response schema. These are an implementation option, not an activated service. Function calling · Structured Outputs

05 / Booking agent contract

From a proposed action to a real receipt

ToolEffectAuthorization
search_experiencesRead destination catalog and inventory.Read-only, scoped to the requested city and date.
get_booking_quoteGet provider price, fees, currency, expiry and terms.Read-only. Check any supplier-specific side effects.
propose_actionsWrite a draft task batch owned by the traveler.Authenticated traveler; no supplier action.
execute_approved_bookingReserve or confirm specified items through a supplier.Backend validates approval ID, exact quote hash, traveler IDs, charge currency, spend ceiling and expiry.
schedule_trip_reminderQueue a trip-related email to the verified traveler address.Explicit reminder opt-in; linked to a confirmed booking.
get_task_statusRead state and provider receipts.Owner or authorized support staff only.

State model: Draft → Needs approval → Approved → Queued → Running → Confirmed. Additional states: Needs review, Reconciling, Failed, Paused and Cancelled. A provider receipt, signed callback or authoritative status query is required for Confirmed.

  • Use an idempotency key for each approved item and attempt. After a timeout, query the provider before retrying. Queue delivery does not guarantee a one-time external charge.
  • Model a batch as separate items. If one booking succeeds and another fails, show the confirmed item and the remaining action. Do not silently cancel successful reservations.
  • Pausing stops unstarted tasks. It does not cancel a confirmed ticket or stop an already-submitted provider request. Cancellation uses a separate policy and approval.
  • Use the payment provider’s hosted checkout when payment is required. Do not collect card details in chat or pass them to the model.
  • For suppliers without a supported booking API, hand off to their checkout. “Continue on provider site” remains distinct from “Confirmed.”

Extend the current Supabase foundation

Keep current booking and inventory transactions. Add provider references and the distinction between an internal reservation and an external confirmed ticket. Extend money fields to explicit currency plus integer minor units before supporting supplier charges in CNY or SGD; never relabel existing THB values.

  • Protect traveler records with ownership checks and RLS. Keep staff roles in trusted server-managed records. An agent’s task can act only for its authenticated owner and granted scope.
  • Store API keys in server-side secrets. Send the AI only the trip context it needs; payment credentials and full identity documents stay out of prompts and logs.
  • Use a durable task queue and scheduled worker. Store reminder due times in UTC, calculate them from the experience’s IANA timezone, and include local time in the message.
  • On cancellation or rescheduling, cancel or replace pending reminders with a new deduplication key. If booking occurs within 24 hours, send the chosen immediate itinerary notification instead of a reminder dated in the past.
  • Retry transient email failures with bounded backoff. Record provider acceptance and delivery webhooks separately. Stop on opt-out or permanent bounce; suppress duplicate sends.
  • Transactional trip email is separate from Supabase Auth confirmation email. Configure the sender domain and delivery provider before either is described as ready.

Decisions needed for stage 2 onward: AI provider and budget; initial ticket supplier and sandbox access; payment responsibility; email provider and sending domain; public hosting URL; retention policy and support owner.

Success measures: completed brief-to-itinerary rate, valid recommendations, quote-to-confirmation rate, duplicate charge count, task failure and recovery rate, reminder delivery outcomes, model cost per useful plan and traveler satisfaction.

Production launch gates: no cross-user data access; no paid action without matching approval; no invented availability or booking reference; no reminders before opt-in; no secrets in browser code; no success state without supporting evidence.
